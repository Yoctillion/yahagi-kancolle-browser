# Building and Verifying from Source

[简体中文](BUILDING.md) ｜ English ｜ [한국어](BUILDING.ko.md)

This guide is for anyone who wants to build the Android client or contribute to its development. To install a published version, use [GitHub Releases](https://github.com/yamatosaki/yahagi-kancolle-browser/releases). The source on the default branch may be ahead of the published app. If you need the source for a specific release, check out the corresponding tag from the release page and follow the configuration at that tag.

## Development Environment

The current [CI configuration](.github/workflows/ci.yml) uses:

- Flutter **3.44.8 stable**. Dart is included with Flutter; see `pubspec.yaml` for the version constraint.
- JDK **17**. Set `JAVA_HOME` to JDK 17 when running the native Android tests.
- The Android SDK, command-line tools, and build components with their licenses accepted. The Flutter SDK determines the `compileSdk` and NDK versions; see `android/app/build.gradle.kts`.
- Git and Python 3. The Python data build tests also require Pillow.

Install these tools, then check your environment with `flutter doctor -v`. You can review and accept the Android licenses with `flutter doctor --android-licenses`. The first build needs to download dependencies for Flutter, Pub, Gradle, and Android.

## Get the Source and Build a Debug APK

Run the following commands in a terminal:

```sh
git clone https://github.com/yamatosaki/yahagi-kancolle-browser.git
cd yahagi-kancolle-browser
flutter pub get
flutter build apk --debug
```

The generated APK is at `build/app/outputs/flutter-apk/app-debug.apk`. With a device connected for debugging, you can also use `flutter run`.

Debug builds use a debug signing key generated automatically on your machine. They do not require the maintainer's signing keys, account data, game databases, or backup files. Machine-specific configuration, such as the Android SDK path, is generated by the tools and should not be committed to the repository.

## Verification Commands

Run the checks corresponding to CI from the repository root:

```sh
python -m pip install pillow
python -m unittest tool.test_check_repository_hygiene -v
python tool/check_repository_hygiene.py
python -m unittest tool.test_build_sortie_release tool.test_build_enemy_release tool.test_verify_data_release -v
dart run tool/verify_data_release.dart
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
```

To run the native Android unit tests in Windows PowerShell:

```powershell
.\android\gradlew.bat -p android :app:testDebugUnitTest --console=plain
```

On Linux or macOS:

```sh
chmod +x android/gradlew
./android/gradlew -p android :app:testDebugUnitTest --console=plain
```

Some integration tests use raw samples kept only on local development machines. These tests explicitly skip when the samples are absent from a public checkout. The public tests using synthetic data do not require real accounts or game API dumps. Do not add raw data to the repository just to run the local integration tests.

## Release Signing

`flutter build apk` selects release mode by default. This mode requires your own signing configuration. When first checking whether the source builds, use the `--debug` command above.

To make your own release APK, keep the signing configuration outside the repository and set the `YAHAGI_SIGNING_PROPERTIES` environment variable to its file path. The configuration fields are `storeFile`, `storePassword`, `keyAlias`, and `keyPassword`; see `android/app/build.gradle.kts` for how they are read. Once configured, run `flutter build apk --release`.

Do not commit keys, signing configuration, local SDK configuration, app packages, logs, or record backups. For third-party code and resource licenses, see [THIRD_PARTY_NOTICES](THIRD_PARTY_NOTICES). For contribution requirements, see the [Contributing Guide](CONTRIBUTING.en.md).
